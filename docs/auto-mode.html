MXFrame Auto Mode

What the engine does when you call compute(device="auto") on a machine with a CPU and a GPU, drawn from the code on the auto-mode branch and the numbers measured on the reference box (Ryzen 9 5900X, 24 threads; RTX 3090 on PCIe 4.0 x8).

The short version

What it does not do

Stream every query's rows through a shared morsel queue to the CPU and the GPU at once. That scheduler is built and tested (coproc.run_router), but it lost on this hardware: moving host data over the link is slower than all 24 cores reading RAM.

What it does

Picks the cheaper device per query from measured costs, runs first scans on the CPU, copies hot columns to the GPU in the background, and on later queries splits the rows: the GPU takes its resident slice while every CPU core takes the rest, at the same time.

1 · Every query: plan, price, place

Before running anything, auto mode rewrites the plan and prices it on each device using this machine's calibration (mx.calibrate(): per-kernel cost fits, link bandwidth, GPU start-up). Filters and copies to the GPU count against the GPU; the GPU has to win by 10% or the CPU runs it.

A CUDA error also switches the GPU off for the rest of the process; any GPU path not verified against DuckDB is never chosen.

2 · One session: how the GPU gets involved

The GPU pays off once the data already lives there. So the first scan of a table runs on the CPU, and after it returns the table's columns are copied to the GPU in the background. The copy pauses whenever another query is running. From then on, a repeat query over that table splits its rows between both devices.

Measured, TPC-H SF10 Q1, one session, 0.5 s between queries: CPU-only 177 · 58 · 58–65 ms. Auto 185 · 71–73 · then 43–49 ms.

3 · The split: one slice each, then merge

For an aggregation the fused kernel reads each row once and keeps a running total per group, so any slice of rows can run anywhere and the totals just add up. Auto mode picks the GPU's share so both devices finish at the same moment, starting from calibration and tuning itself from each run's timings.

4 · Why this design, in numbers

Same query and data every time: the fused aggregation stage of SF10 Q1 over 60M rows. Bars are to scale.

  • The link is the bottleneck. Host memory feeds all CPU cores at roughly 40–50 GB/s; the GPU's PCIe 4.0 x8 link carries about 10–13 GB/s. Shipping rows mid-query can't keep up with the CPU reading them in place.
  • Once columns are resident, the GPU is fast, and splitting beats both devices: 25 ms against 57 (CPU) and 39 (GPU).
  • One call per device beats many morsels on the GPU: each GPU call has about 4.5 ms of fixed cost, so a dynamic queue of small GPU morsels (42 ms) loses to one static slice (25 ms).

What's not in auto mode yet

  • Joins on the GPU. Joins run on the CPU through the new join engine; placing large joins on the GPU per operator is ticket F-007.
  • Streaming co-processing for first scans. Not worth it on PCIe x8. It becomes interesting on PCIe 5 or unified-memory machines (Grace Hopper, Apple silicon), where the router already exists.
  • A native Parquet reader. Reading stays on PyArrow for now (F-021); on raw scans that is mxframe's largest remaining gap to Polars.
