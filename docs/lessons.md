- 2026-09-29 · Mojo `parallelize` called from a `.so` loaded by ctypes segfaults (no async runtime in a host process): call `KGEN_CompilerRT_AsyncRT_GetOrCreateCPUDevice` first, as in `kernels_aot/pipeline_cpu.mojo`.
- 2026-09-29 · The stdlib `Atomic` is sequentially consistent, so NVPTX fences around every atomic (float64 shared-memory accumulation ran ~100x slower than it should): use `llvm.atomicrmw` with monotonic ordering for accumulation (`_atomic_add_f64` in `kernels_aot/pipeline_gpu.mojo`). Separately, float64 compares run at 1/64 rate on GeForce: compare columns in their own type (CMPC), not widened to float64.
- 2026-09-29 · A Bool captured by a `@parameter` GPU kernel closure was read wrong (all rows went to group 0); compute such flags inside the kernel from Int arguments, and write GPU kernels as plain `def`s with explicit arguments.
- 2026-09-29 · The existing GPU sort/gather post-op rounds every float64 column to float32 (sums off by 1 part in 1e8); sort small aggregate results on the CPU.
- 2026-09-30 · GPU 1 is shared with other agents (fixed launch cost jumps 0.1 ms to 6.7 ms when busy): compare kernel variants back to back in one script and quote `_repeat` steady-state numbers, never single runs.
- 2026-09-30 · Comparing float32 data with a decimal literal in float64 drops every row equal to the literal (TPC-H Q6 lost 54% of its revenue on CPU): a float32 column takes the literal as float32, like DuckDB, Polars and NumPy 2.
- 2026-09-30 · A cache keyed by `id(obj)` must hold a reference to `obj` and check identity on lookup; ids are reused after garbage collection, which returned another table's results (found in F-010 review).
- 2026-09-30 · Judge correctness against DuckDB, never against our own CPU path: GPU Q6 (8.865e7) looked wrong next to CPU (4.07e7), but DuckDB gives 8.865e7 — the CPU path dropped boundary rows comparing float32 columns to float64 literals. GPU paths not yet verified against DuckDB go in `auto_mode.KNOWN_BROKEN_GPU`.
- 2026-09-30 · A DuckDB reference over the raw float32 columns shares the data's own errors (the generator truncated 0.05 to 0.049999997, so Q6 "matched" at 8.865e7 while the official answer is 123141078.2283): build the reference through views that restore DATE and DECIMAL(15,2), and check known official answers (Q6 SF1).
- 2026-09-30 · A result cache must be keyed by everything that changes the result, device included: `_JOIN_RESULT_CACHE` without it let `device="gpu"` tests reuse the CPU's join, so the GPU join path (and its SF10 out-of-memory) was never exercised.
- 2026-09-30 · The Mojo device-context memory manager reserves ~90% of free GPU memory when the first kernel-side buffer is created (the recursive scan at >= 1M rows), starving our own cuMemAlloc and every other process on the GPU: `aot_kernels` sets `MODULAR_DEVICE_CONTEXT_MEMORY_MANAGER_SIZE_PERCENT=25` before any GPU use. Observed with a 5% pool: `sort_topk` of 250M rows printed `oom log` on stderr and returned all-zero indices with no exception (kernels swallow errors); the scan was not seen to fail that way, but `hash_join` now raises if its prefix sum is 0 over non-zero counts.
- 2026-09-30 · `pyarrow.Table.join` defaults to a LEFT OUTER join: pass `join_type="inner"`.
- 2026-09-30 · On the query path never call pa.array / pa.scalar / Array.to_numpy / fill_null(<python value>) / compute with Python literals / pq.read_table: PyArrow then imports pandas (~150-200 ms per fresh process). Use np_arrow.array / scalar / to_numpy and ParquetFile; tests/test_np_arrow.py guards it.
- 2026-09-30 · Never chain `git commit` after `pytest ... | tail`: the pipe hides pytest's exit code and a red test got committed. Capture the exit status (`> log; rc=$?`) and commit only when it is 0.
- 2026-09-30 · An operator above an Aggregate (Project, Filter, another Aggregate) or any Aggregate input that is not `Filter*(Scan)` must run on a materialized table (`_materialize_barrier`): the aggregate paths only look at the Scan under them and used to ignore what sat above or between. Add a fuzz seed (tests/test_f016_fuzz.py) when a new plan shape breaks.
- 2026-09-30 · A numeric literal next to an array takes the array's type in arithmetic (`_arith_operands`): a float32 literal array turned `int + 2` into float32 and rounded `float64 + 0.1`.
- 2026-09-30 · A plan shape the fused pipeline declines falls to the `gpu_aot` path, which accumulates float64 in float32 (fuzz seed 5061): when a new plan shape reaches the GPU, check `last_compile_provenance["path"]` is `fused_pipeline_*`, and inline a Project under a grouped Aggregate before `try_fused_aggregate`.
- 2026-09-30 · A scan's column pruning works on names the query uses, but a join renames clashing right columns (`x` -> `x_right`): keep the source column whenever a referenced name is its renamed form (`io_parquet._renamed_ref`).
- 2026-09-30 · `pyarrow.parquet` row-group stats and `ParquetFile.schema_arrow` report dictionary types when `read_dictionary` is set: look through them (`_kind`) before deciding a column is not a string.

- 2026-09-30 · Every caller of AOTKernels.sort_indices (radix sort) must verify the result is a sorted permutation and fall back to np.argsort: one bad order was seen once and never explained, and F-020's group encoder skipped the check (review caught it).
- 2026-10-12 · A shortcut guard (here `n_codes * 16 < n`) can make a test silently exercise the fallback instead of the new path: assert the new path ran (non-None result, provenance), not only that the answer is right.
- 2026-10-12 · A per-query "within X%" check on 50–400 ms first runs is mostly noise in one run (SF1 auto vs cpu: 17–21/22 across 4 runs of the same code): judge it on the median of several fresh-process runs, and report every single-run count, not the best one.
- 2026-10-12 · Don't name the cause of a benchmark loss, or title a ticket by a cause, without a measurement that isolates it; and drop queries whose isolated time is worse than the combined one before splitting a sum (they measure something else). benchmarks.md blamed decode for five queries; the engine-only run showed it held for some, not all.
- 2026-10-12 · PyArrow imports pandas whenever it builds an empty array from Python (`pa.array([])`): zero-chunk `combine_chunks()` / `to_numpy()`, masked NumPy input, an empty `isin` list, and also `Table.group_by` / `Table.join`. Use `np_arrow.combine` / `value_set` / `array`; tests/test_no_pandas_tpch.py runs all 22 queries on tiny data, where empty intermediates actually occur.
- 2026-10-12 · In a native pipeline, don't materialize an n_rows-sized intermediate (a 240 MB group-id array made SF10 Q1 156 ms; encoding keys per 64k-row morsel and aggregating at once made it 66 ms). And time first runs in fresh processes: warm repeats reused freed pages and hid the cost.
- 2026-10-12 · Judge a start-up optimization on import + first query together in a fresh process: preloading the Mojo runtime cut the first query 23 → 5 ms but grew `import` 124 → 143 ms (dlopen serializes on the loader lock), the same total.
