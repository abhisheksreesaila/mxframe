- Check first (review of F-053): a `read_parquet` frame may never find its data resident: sources are re-read on each compute and residency is keyed by buffer addresses. Verify a repeat query finds its columns resident before relying on resident-data splits.
- [x] answer to the check (2026-10-16, probe on a 3M-row file): `read_parquet(path)` once and queried repeatedly, and an in-memory table, found their columns resident (the frame holds one table, so buffer addresses repeat). A **new** `read_parquet(path)` per query, and every `scan_parquet` compute (it re-reads the file into new buffers each time, even on the same frame), never did: the upload was freed as soon as that query's table died. Fixed: a table read from a file carries a source token (`io_parquet.source_token`: path, device, inode, mtime, size, columns read, pushed filters, final column types) and the device copy is keyed by it plus the group-id fingerprint (`coproc_fused.gid_fingerprint`: a hash of the keys in id order, so ids from a re-encoding mean the same groups). An entry keyed this way holds no host buffers and lives until evicted or the file changes (a changed file frees its old copies at the next upload; a different filter pushed into the read is a different source). In-memory tables stay keyed by buffer address. `tests/test_f057_coproc.py::test_repeat_queries_over_the_same_source_find_it_resident` (scan_parquet, read_parquet, in-memory), changed file, pushed filters
- [x] the native CPU executor takes the CPU share of a split: `native_exec.range_partials` runs `mx_execute` over `table.slice(start, end - start)` (zero-copy, no change to the executor), grouping by the group ids as a column, and returns the `Partials` the pipeline kernel would, which merge with the GPU's. Every aggregate kind (sum, mean, count, min / max with and without NaN: the NaN-count slot is rebuilt from the executor's NaN-aware result), global and keyed. Count distinct is not splittable (not a fused-pipeline shape). Under the policy the native executor still declines the whole plan (so it never runs beside the GPU's share unasked); the fused path's CPU work (the split's share, or all rows when the data is not resident) goes through it, the older pipeline kernel only if the executor declines a range. Rough A/B on a loaded machine (load 21-25; noisy): `range_partials` adds ~0.3 ms of Python per call; on a 12M-row, 4-group, 5-aggregate query the older kernel was ~20% faster than the executor alone (11.3 vs 13.9 ms), so the split's CPU half is slower than it could be for that shape (F-053 saw the same, 6.9 vs 7.7 ms): a per-shape choice of the CPU share's engine waits for the quiet-machine run
- [x] a split is chosen only where calibration predicts it beats both single devices by 10% (`coproc_fused.plan_split`): the CPU share runs 5% slower beside the GPU (an unmeasured allowance: a resident GPU share reads no host memory), the GPU pays 4.5 ms per call on top of its calibrated compute, the partials cost a merge (0.5 ms plus ~4 GB/s over groups x slots), and the split must save 10% against the faster of CPU alone and GPU alone. The decision also needs the columns resident (`coproc_fused.resident_for`); otherwise the query runs native with no policy and an upload is queued for after it returns (`pipeline_exec.queue_resident_upload`), so a first query is exactly `device="cpu"` (before this the first query of a predicted split ran the older pipeline). `explain` prints the numbers (`cpu path: cpu+gpu split (est ... gpu share ... cpu alone ... contention ... gpu alone ... merge ... vs best single device ...: +N%, needs 10%)`, or why not) and, after a run, the estimated and actual split times next to each device's busy time. On this box's calibration a 6M-row Q1-shaped query is never split (GPU 1.9 ms + 4.5 ms per call against 5.5 ms of CPU)
- [x] the split predicate matches the split path: `pipeline_exec.split_check` asks the same `_table_of` / `_bind` the fused pipeline runs (Project below the aggregate is inlined first, as `compile_and_run` does), `CustomOpsCompiler._arrow_aggregate_reason` (nulls in any column the plan reads, integer sums that could pass 2^53: the Arrow path answers those before the pipelines), stable group keys, and, for an in-memory table, columns with stable buffers (dictionary-code filters, bool and narrow-int columns are converted on every query). A table read from a file may have converted columns resident too (its token fixes the codes). ## F-008 Fused pipeline kernel: vectorized interpreter [done]
Needs: F-002 · Files: `kernels_aot/pipeline*.mojo` (new), `pipeline_program.py` (new: Expr → bytecode), dispatch in `custom_ops.py`
Why: SF10 Q1 spends ~1.3 s in PyArrow expression eval, NumPy mask indexing and dtype copies around a ~0.5 s kernel; JIT-compiling a kernel per query shape would cost seconds on a first run.
Design (MonetDB/X100-style vectorized interpretation, AOT, no JIT):
- Python compiles the query's filter predicate, the aggregate input expressions and the aggregate list into a small bytecode program (LOAD_COL i, CONST k, ADD/SUB/MUL/DIV, CMP_{LT,LE,GT,GE,EQ,NE}, AND/OR/NOT, BETWEEN, IN_SET (dictionary codes), plus AGG_{SUM,MIN,MAX,COUNT} slots). Registers are vectors.
- CPU kernel: `parallelize` over morsels; within a morsel process vectors of ~1–2K rows: evaluate the predicate into a selection vector, evaluate expressions into cache-resident register vectors (SIMD), accumulate into per-thread float64 partials per group; merge partials at the end. Input columns are raw pointers (int32/int64/float32/float64 + int32 group ids, or none for global aggs).
- GPU kernel: same bytecode, one thread per row (bytecode is uniform across threads, so no divergence), block-level partials (shared memory for small group counts, global atomics otherwise).
- Both entry points take a row range [start, end), so the F-006 Router can hand morsels to either device, and return partials the Router merges.
- [x] Q1, Q6, Q14, Q19-style filters + arithmetic + grouped/global aggregates run through it on both devices; results match DuckDB (float64 accumulation)
- [x] fused stage on SF10 Q1 (60M rows, group ids ready) < 100 ms on `cpu`; cold end-to-end time is tracked in F-009
- [x] unsupported expressions fall back to the existing path, never wrong results
