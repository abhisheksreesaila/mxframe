## F-057 Morsel co-processing that wins [done]
Needs: F-053, F-055 · Builds on F-006 (`coproc.py`, `coproc_fused.py`, the Router) · Agreed 2026-10-15
- [ ] research first (added to `docs/spec-auto-mode.md`): morsel-driven parallelism (Leis 2014), HetExchange, "Pump Up the Volume" and later CPU+GPU co-processing work; what F-006 measured (PCIe x8: streaming host data loses to CPU, resident data splits win) decides which ideas are worth it on this hardware
- Research (2026-10-15, `docs/research/cpu-gpu-coprocessing.md`): keep F-006's design (host data -> CPU, resident data -> static split, one GPU call; Mordred 2022); split only if predicted time beats the faster device by 10% after per-call (4.5 ms), merge and contention costs; CPU threads take late GPU work; the second GPU as a third worker with its own resident share
- Check first (review of F-053): a `read_parquet` frame may never find its data resident: sources are re-read on each compute and residency is keyed by buffer addresses. Verify a repeat query finds its columns resident before relying on resident-data splits.
- [x] answer to the check (2026-10-16, probe on a 3M-row file): `read_parquet(path)` once and queried repeatedly, and an in-memory table, found their columns resident (the frame holds one table, so buffer addresses repeat). A **new** `read_parquet(path)` per query, and every `scan_parquet` compute (it re-reads the file into new buffers each time, even on the same frame), never did: the upload was freed as soon as that query's table died. Fixed: a table read from a file carries a source token (`io_parquet.source_token`: path, device, inode, mtime, size, columns read, pushed filters, final column types) and the device copy is keyed by it plus the group-id fingerprint (`coproc_fused.gid_fingerprint`: a hash of the keys in id order, so ids from a re-encoding mean the same groups). An entry keyed this way holds no host buffers and lives until evicted or the file changes (a changed file frees its old copies at the next upload; a different filter pushed into the read is a different source). In-memory tables stay keyed by buffer address. `tests/test_f057_coproc.py::test_repeat_queries_over_the_same_source_find_it_resident` (scan_parquet, read_parquet, in-memory), changed file, pushed filters
- [x] the native CPU executor takes the CPU share of a split: `native_exec.range_partials` runs `mx_execute` over `table.slice(start, end - start)` (zero-copy, no change to the executor), grouping by the group ids as a column, and returns the `Partials` the pipeline kernel would, which merge with the GPU's. Every aggregate kind (sum, mean, count, min / max with and without NaN: the NaN-count slot is rebuilt from the executor's NaN-aware result), global and keyed. Count distinct is not splittable (not a fused-pipeline shape). Under the policy the native executor still declines the whole plan (so it never runs beside the GPU's share unasked); the fused path's CPU work (the split's share, or all rows when the data is not resident) goes through it, the older pipeline kernel only if the executor declines a range. Rough A/B on a loaded machine (load 21-25; noisy): `range_partials` adds ~0.3 ms of Python per call; on a 12M-row, 4-group, 5-aggregate query the older kernel was ~20% faster than the executor alone (11.3 vs 13.9 ms), so the split's CPU half is slower than it could be for that shape (F-053 saw the same, 6.9 vs 7.7 ms): a per-shape choice of the CPU share's engine waits for the quiet-machine run
- [x] a split is chosen only where calibration predicts it beats both single devices by 10% (`coproc_fused.plan_split`): the CPU share runs 5% slower beside the GPU (an unmeasured allowance: a resident GPU share reads no host memory), the GPU pays 4.5 ms per call on top of its calibrated compute, the partials cost a merge (0.5 ms plus ~4 GB/s over groups x slots), and the split must save 10% against the faster of CPU alone and GPU alone. The decision also needs the columns resident (`coproc_fused.resident_for`); otherwise the query runs native with no policy and an upload is queued for after it returns (`pipeline_exec.queue_resident_upload`), so a first query is exactly `device="cpu"` (before this the first query of a predicted split ran the older pipeline). `explain` prints the numbers (`cpu path: cpu+gpu split (est ... gpu share ... cpu alone ... contention ... gpu alone ... merge ... vs best single device ...: +N%, needs 10%)`, or why not) and, after a run, the estimated and actual split times next to each device's busy time. On this box's calibration a 6M-row Q1-shaped query is never split (GPU 1.9 ms + 4.5 ms per call against 5.5 ms of CPU)
- [x] the split predicate matches the split path: `pipeline_exec.split_check` asks the same `_table_of` / `_bind` the fused pipeline runs (Project below the aggregate is inlined first, as `compile_and_run` does), `CustomOpsCompiler._arrow_aggregate_reason` (nulls in any column the plan reads, integer sums that could pass 2^53: the Arrow path answers those before the pipelines), stable group keys, and, for an in-memory table, columns with stable buffers (dictionary-code filters, bool and narrow-int columns are converted on every query). A table read from a file may have converted columns resident too (its token fixes the codes). The model is priced first and the check (a pass over int64 columns, remembered per table) runs only when the model likes a split. `tests/test_f057_coproc.py::test_split_predicate_matches_what_the_split_path_takes` (13 shapes)

## F-006 Router co-processing for grouped and global aggregates [done]
Open for Abhishek: the two unticked items below are not achievable on PCIe x8 for host data (measured); keep them as future-hardware goals or drop them.
Needs: F-002, F-003, F-005 · Files: `coproc.py` (new), hook in `custom_ops.py`
Done so far: `auto_mode.Placer` (cpu/gpu/split cost decision), `coproc.run_router` (morsel queue, prepare/compute overlap, fallible GPU worker), `gpu_stream.DeviceStager` (pinned slots, async H2D), `residency.ResidencyTracker` (LRU GPU copies, pins).
Physics on the reference box (measured 2026-09-29): GPU link is PCIe 4.0 **x8** — pinned H2D 13.4 GB/s, pageable 11 GB/s, stager ~9 GB/s; host DRAM (Ryzen 5900X, dual-channel DDR4) ~40–50 GB/s. So a scan-aggregate over host-resident data is ~4× faster on all CPU cores than shipping it to the GPU, and splitting a pure scan gains little (both devices read the same DRAM). The GPU earns its keep on (a) joins / high-cardinality group-bys (CPU latency-bound), (b) repeat queries over GPU-resident columns, (c) idle-link background upload of hot columns during CPU-bound queries so the next query finds them resident.
Design as built (measured 2026-09-30, SF10 Q1 fused stage, 60M rows): CPU 57 ms, GPU from host 353 ms, GPU resident 39 ms, CPU 40% + GPU 60% resident 25 ms; a Router streaming host data to the GPU was 67–160 ms (worse than CPU), and a dynamic morsel queue on resident data 42 ms (each GPU call has ~4.5 ms fixed cost). So `coproc_fused`: host data → CPU + background upload of the query's columns and group ids; resident data → static split, one GPU call + multi-core CPU, fraction balanced from calibration and refined by `observe`. Break-even (fresh process, public API, SF10 Q1, re-measured after moving all CUDA calls off the query thread): run 0 is ~1.0–1.2 s with or without co-processing (cold costs unrelated to it, see F-015); runs 1–2 pay the one-time GPU warm-up of the split (57–107 ms vs 51–96 ms); from run 3 on the split is 38–45 ms vs 51–60 ms CPU-only.
- [x] decomposable aggregations run on both devices at once; partial aggregates merged (Router, static split)
- [x] split ratio from calibration (refined online); `gpu_fraction=` overrides; results identical to `cpu` for 1, 2 and all threads (tests)
- [x] GPU failures inside a split are redone on CPU; CUDA errors disable the GPU; residency never serves a stale or freed device copy (pinned entries, owners held, zero-copy columns only)
- [x] `profile=True` / explain show both devices' busy time
- [ ] streaming host data to the GPU with copy/compute overlap beats CPU-only on this box — not achievable on PCIe x8 (measured above); revisit on PCIe 5 / Grace Hopper hardware
- [ ] cold (first-query) SF10 Q1 under `auto` beats `cpu` by ≥ 15% — not on this box for host data (see break-even); met for repeat queries

## F-008 Fused pipeline kernel: vectorized interpreter [done]
Needs: F-002 · Files: `kernels_aot/pipeline*.mojo` (new), `pipeline_program.py` (new: Expr → bytecode), dispatch in `custom_ops.py`
Why: SF10 Q1 spends ~1.3 s in PyArrow expression eval, NumPy mask indexing and dtype copies around a ~0.5 s kernel; JIT-compiling a kernel per query shape would cost seconds on a first run.
Design (MonetDB/X100-style vectorized interpretation, AOT, no JIT):
- Python compiles the query's filter predicate, the aggregate input expressions and the aggregate list into a small bytecode program (LOAD_COL i, CONST k, ADD/SUB/MUL/DIV, CMP_{LT,LE,GT,GE,EQ,NE}, AND/OR/NOT, BETWEEN, IN_SET (dictionary codes), plus AGG_{SUM,MIN,MAX,COUNT} slots). Registers are vectors.
- CPU kernel: `parallelize` over morsels; within a morsel process vectors of ~1–2K rows: evaluate the predicate into a selection vector, evaluate expressions into cache-resident register vectors (SIMD), accumulate into per-thread float64 partials per group; merge partials at the end. Input columns are raw pointers (int32/int64/float32/float64 + int32 group ids, or none for global aggs).
- GPU kernel: same bytecode, one thread per row (bytecode is uniform across threads, so no divergence), block-level partials (shared memory for small group counts, global atomics otherwise).
- Both entry points take a row range [start, end), so the F-006 Router can hand morsels to either device, and return partials the Router merges.
- [x] Q1, Q6, Q14, Q19-style filters + arithmetic + grouped/global aggregates run through it on both devices; results match DuckDB (float64 accumulation)
- [x] fused stage on SF10 Q1 (60M rows, group ids ready) < 100 ms on `cpu`; cold end-to-end time is tracked in F-009
- [x] unsupported expressions fall back to the existing path, never wrong results

## F-107 Test process hangs on a futex while other suites share the GPUs [review]
Seen three times on 2026-10-16 (F-070 developer, F-094 review, a main-repo run): a full-suite process idles at ~0% CPU for 30+ minutes, 145 threads in `futex_do_wait`, holding the GPU device handles, while 3-4 other suites use the same GPUs. - [x] capture a stack: the test runner now dumps all threads after 15 minutes stuck (`faulthandler_timeout=900`); keep suite output in a file (lessons). ptrace is blocked here, so the dump is the only way
- [x] from the dump, find the waiting lock(s); if it is ours, fix the lock order and add a stress test (concurrent queries + background upload + warm-up); if it is the driver under cross-process contention, document it and make the GPU tests serialize on a file lock

Finding (no dump was needed; found by reading the lock sites, reproduced deterministically): `coproc_fused._evict`, the `weakref.finalize` callback on a cached input's owner, took the non-reentrant `coproc_fused._lock`. A finalizer runs on whichever thread drops the last reference or runs the cyclic GC, and a GC can start at any allocation, including inside `with _lock:` (`_start_thread` holds it across `Thread.start()`, which allocates; so does every other locked block). The thread then waits for itself: main thread idle, all other threads parked in `futex_do_wait`, last stack in `try_split` -> thread start. Load only changes when the GC fires. Not the CUDA driver, not cross-process.
Fix: `_evict` never blocks; it queues the key and evicts at once when the lock is free, else `_drain_evictions()` (blocking, called before every cache lookup: `_acquire`, `_start_upload`, `resident_for`, `clear_residency`) does it, so a dead owner's entry is still never found. Same pattern removed in `aot_kernels._get_cuda_driver` and `gpu_stream._driver` (DeviceArray `__del__` calls them while the init holds their lock): lock-free fast path once built.
Tests: tests/test_f107_lock_reentry.py (3, child processes with timeouts; two hung before the fix).
